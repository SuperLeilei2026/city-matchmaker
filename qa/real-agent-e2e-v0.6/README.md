# v0.6 真实模型端到端验收

2026-10-14 在 macOS OctoSense Shell 中，从本地签名目录全新安装 `毕业第一站` v0.6.0，并以合成的小陈式档案完成“留下两城 → 三幕平局 → 系统 Agent 决胜提问 → 确认核验任务 → 选择先验证城市 → 重启恢复”的完整流程。

这次验收确认的是运行边界，不是推荐准确率。事实是：MiniMax-M3 在宿主内完成了一次真实调用；应用只把问题与任务作为提案展示；用户确认前，核验任务和先验证城市均保持为空；重启后双城通行证和已确认内容保持不变。

## 结果

- 最终城市：深圳、杭州。
- 原始倾向：`我更倾向深圳，因为深圳成本低、具身智能机会更多。`
- 三幕选择：全部“还看不出来”。三次平局没有自动产生赢家。
- Agent 关键一问：`你把“潮湿闷热”列为健康红线。深圳与杭州一年里哪边更容易长期闷热需要除湿？先核这一项再谈别的。`
- 核验任务：`两城各联系一位现居住满半年的租户，请他们描述4到10月室内湿度、是否长期开除湿、以及通勤时段室外闷热的真实感受。`
- 用户最后选择先验证深圳；杭州仍作为备选保留。

## 已验证边界

1. 首次模型调用前，OctoSense 展示宿主同意界面；同意后调用才继续。
2. 发送给模型的健康红线是人类可读的“潮湿闷热”，不是内部数字 ID。
3. 模型返回符合 `DQ1` 协议，城市 ID、资料版本、对局版本、维度和长度均通过应用校验。
4. 收到提案后，只有提案字段发生变化；清空提案字段即可还原调用前状态哈希。
5. 点击“加入核验清单”后，只有已确认任务字段写入。
6. 点击“先验证 深圳”后，先验证城市才写入。
7. 退出并重新启动同一安装，通行证界面显示“已恢复本机进度”，存档 SHA-256 与退出前相同。

## 尚未证明

单个合成场景不能证明城市推荐“准确”、用户会更快乐，也不能替代小陈和小雷的真人试用。Kimi、移动端、鸿蒙端、模型故障切换、真实岗位与房源核验也未在本次验收中覆盖。
