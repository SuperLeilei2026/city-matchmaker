# Joy City v0.3：项目定位与参赛场景

更新：2026-10-03。本轮更新产品实际能力与证据边界，没有重新联网核验赛事规则，也没有改变外部报名记录。下列官方链接沿用此前登记材料，当前要求仍以主办方发布为准。

## 产品定位

**面向 AI 应用与产品人群的城市生活探索。** 先把新鲜感、恢复精力、关系、职业期待和不确定性接受方式写成可修改画像，再认识一城，通过心动点与代价反馈修订一个场景，形成下一步值得亲自验证的候选。

对外的一句话：**给想做 AI 产品的你，从一周怎么过，找到想去了解的城。**

`aiRole` 用来界定产品、搭建、设计、运营或探索方向，不预测具体岗位录取。当前不是路线导航、自动求职、房源匹配或幸福概率预测。INTP 小猫侧重职业发展，ENFP 小狗侧重生活心动，排序可以不同；事实、来源与硬条件必须一致。

## 这一版能展示什么

| 能力 | 已有实现或证据 | 不能据此声称 |
| --- | --- | --- |
| 五维生活画像 | 明确场景选项、可修改短句和来源路径；旧资料空值迁移 | 从人格标签推断真实需求，或五维心理模型已被验证 |
| 城市比较 | 八城、共享权重、气候底线、明确拒绝、相近候选与来源 | 唯一最优城市、喜欢概率、录取率或创业成功率 |
| 证据不足处理 | 136 个 Joy 信号中 47 个 editorial、89 个 unknown | 五维已全部具有有效的城市区分能力 |
| 手动反馈修订 | 心动或受不了的维度引出一问，明确改选后重算 | 所有反馈都必须导致改推，或 Web 使用了大模型 |
| 体验验证行动 | 按明确的不确定性、关系与恢复选择，生成三条下一步；空白则澄清 | 据此推断当地条件已满足，或行动一定提高满意度 |
| 原生一致性 | 配置共享、旧存档迁移、原生与 JavaScript 合成案例对照 | 真实用户满意或真实模型成功 |
| Agent 执行机制 | CM1 提案白名单、确认、拒绝、失效处理、保存与读回检查 | Agent 已能修改五维，或注入测试等于真实模型返回 |

关系稳定性、靠近重要的人、职业持续性和全部不确定性选项等资料缺口，当前不会制造城市差异。五维画像可用与五维推荐有效是两件尚需分别验证的事。

不确定性、关系和恢复偏好同时参与体验行动生成，帮助用户决定怎样试、验证什么。这是显式选择到行动建议的规则映射，不是补造城市事实或对未知资料暗中加分。

## 与此前官方场景说明的关系

此前材料记录：官方列出的场景包括导航、写作与创作等，没有独立的“城市推荐”名称，并说明选题可联动、统一参评。本轮不将这一历史记录包装成对最新规则的复核。

- 最准确的产品分类是城市探索与生活决策，可以作为原创场景解释，不能冒充官方独立赛道。
- 与导航、出行有关，但当前没有路线、路况或行程执行，不能声称已完成导航任务。
- 原报名信息为写作与创作。当前主要交付是生活画像、探索候选和分享车票，尚无完整的创作作品编辑流程；不能仅凭城市文案与分享图声称完全贴合原场景。
- 可以展示应用层的反馈理解与受控执行机制。“最佳 Agentic”属于此前材料中的评奖方向，不代表作品已获认可，也不是新增报名场景。

是否需要调整正式登记，仍需参赛者按当前规则与主办方确认。本轮代码和说明更新不发送消息、不更改外部报名记录，也不为贴标签加入无关写作功能。

## Agent 任务的准确演示边界

原生已有的 CM1 任务链是：用户自由反馈 → 系统 Agent 提出白名单内的结构化修改 → 用户确认或拒绝 → 本地应用执行、重算、保存、读回核验。非法、过期、失败或未经确认的响应不能修改资料。

在 v0.3 中必须另外说明：

1. 五维场景目前由手动按钮修改，CM1 不能写入 `joy` 或切换介绍人。
2. CM1 的旧 `priority / focus` 字段即使写入档案，也不影响新的 Joy 排序；不能将其演示成已完成五维理解与执行。
3. 气候避开项和明确拒绝仍可通过受控规则产生实际结果变化；心动不能越过硬条件。
4. 规则负责事实门槛、比较和排除，不能把确定性规则结果写成模型生成的推荐。
5. 当前验证包括真实 card-host 运行和临时包中的显式响应注入；未证明本应用已获得真实模型的成功返回。失败处理通过也不等于模型链路成功。

演示时应分别标明手动场景修订、规则重排、Agent 提案确认和模型服务状态。不得借用旧项目的调用记录，也不得将旧版录屏当作 v0.3 新流程已经录制完成的证据。
