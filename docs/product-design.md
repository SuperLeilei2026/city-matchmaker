# Joy City v0.3：产品设计说明

更新：2026-10-03。本文描述当前实现、产品判断和未验证部分，不把界面完整等同于推荐有效。

## 产品要回答的问题

**找一座，让你愿意留下的城市。** 面向想做 AI 应用、产品、设计、搭建或运营的人，先整理其想过的一周，再介绍值得了解的城市；用户表达心动与代价后，用一个场景选择修正理解。

目标是帮助缩小探索范围、明确生活取舍。当前并不回答哪座城市能让某人“大概率幸福”，也不提供具体岗位录取预测或自动求职。`aiRole` 用于界定方向和画像，还没有细分岗位层面的匹配能力。

## 已实现的体验

| 环节 | 用户做什么 | 应用实际回应 |
| --- | --- | --- |
| AI 方向与背景 | 选择关注的方向；昵称、院校、专业和 MBTI 等可选资料折叠填写 | 不把院校或人格标签转换成能力与城市分数 |
| 五个生活场景 | 分别选择新鲜感、恢复精力、关系、职业期待和不确定性接受方式，也可暂留空白 | 保存明确选择，不把空白补成默认偏好 |
| 天气与现实条件 | 选择想避开的天气及软硬程度；预算、居住方式、通勤可选 | 气候参与比较；实际住房、交通保留为核验项 |
| 可修改画像 | 查看五维短句，点开不准确的一句重新选择 | 每句来自明确选项，保留字段和回答来源，不做心理诊断 |
| 第一次介绍 | 认识一城，看具体理由与代价 | 显示公开资料上的整理判断，保留相近候选与未知条件 |
| 心动与反馈 | 选择心动、受不了、没感觉或明确不考虑；可指出维度 | 反应本身不偷偷改偏好，只有明确拒绝立即移出该城 |
| 再确认一件事 | 重新确认一个相关场景 | 新选择重新计算，原选择可能维持结果；不承诺每次必须换城 |
| 城市车票 | 比较最多三个候选、切换介绍人、看来源、保存 PNG 或复制摘要 | 输出城市与有限生活关键词，不输出完整个人档案 |

Web 目前是 7 步资料界面，之后有独立画像确认页，再进入两轮介绍。两轮是控制体验长度的设计选择，尚无证据证明一次追问足以准确推荐长期生活地。

## 五维画像不等于五维证据齐全

八城资料包括武汉、上海、杭州、成都、广州、南京、北京、深圳，共 32 条来源记录。136 个 Joy 信号位置中，只有 **47 个 editorial 整理判断**，另 89 个为 unknown，没有 Joy 分档被视为 sourced 实测值。

因此，当前实现已经能形成完整的五维自我描述，但城市比较主要靠已有的活动、恢复资源和 AI 交流实践线索。关系维度仅 2 个位置可探索比较；全部 24 个不确定性位置仍未知。稳定关系、离重要的人近、安静的居住环境和职业持续性不能靠城市整体标签推断。

用户选了这些需求，应用会认真记住，却不声称已经据此拉开了城市差距。五维全量有效性尚未验证；如果用户最在意的恰好是未知部分，现有排序的参考价值就更有限。这是下一轮体验验证必须观察的核心问题。

这些回答仍可生成三条具体的体验行动：按不确定性选择尝试节奏，按关系期待选择一种验证方式，按恢复偏好安排普通一天。共享 `buildTrialPlan` 只使用本人明确选择；空白返回澄清提示，不猜当地资源，也不加分。它把“这点暂时不能比较”转为“接下来可以怎样亲自验证”，有效性仍需用户实际体验。

## 两位介绍人

**INTP 小猫侧重职业发展，ENFP 小狗侧重生活心动。** 新用户默认小狗，旧版已选的角色保留。切换介绍人会切换明确展示的维度权重，因此首城可以变化；用户答案、城市事实、引用、明确拒绝和气候底线必须一致。

角色的人格名称属于表达设计，不是对用户的测验。用户 MBTI、星座、年龄和院校不参与排序。城市相处说明是带限制的生活想象与资源介绍，也不能概括全城居民的性格。

暖白纸张、资料夹、中文大字、猫狗形象和带撕线的车票承接原有视觉；这一版把逐场景选择、可修改画像、心动点和生活代价放在主要路径。来源和完整核验清单放在车票背面，既可体验，也能检查。

## 比较方法与解释

[匹配模型](matching-model.md) 和共享配置记录具体权重。小狗给日常生活较大分量，小猫给职业期待较大分量。选气候避开项后，气候占 20%，五维同比缩至 80%。这些是未校准的产品规则，不是用户研究结论。

未知不补成平均数、不作为不适合的证明；所有城市用同一权重。每个候选同时有已知贡献和比较区间。整理判断与未知可能使区间重叠，界面提示“还有相近候选”，不能把首位写成唯一最佳，也不显示喜欢概率。

明确拒绝会改变候选集合；气候硬条件需要充分来源才能排除。预算、合租主卧和单程通勤上限已能记录，但缺乏具体起终点与房源时不用于筛城。产品不应退化成要求用户补齐一大堆现实资料才允许探索。

## 分享与隐私

分享卡表达“我想先了解哪座城，以及想留在生活里的事”。PNG 和摘要只取城市公开介绍及新鲜感、恢复方式短句，不包含昵称、院校、年龄、预算、重要的人位置或自由反馈。

Web 用本机浏览器保存进度，不调用远端模型。旧版升级保留原资料和拒绝记录，五维空值不猜测；清除入口应同时删除当前存档和迁移备份。原生存档与系统 Agent 的数据使用另见隐私说明。

本机分享能力已经实现；是否有人愿意转发、转发能否帮助他人理解自己，尚未验证。旧版录屏不能充当 v0.3 新流程的完整演示证据。

## 接下来优先验证什么

| 产品假设 | 最可能失败的地方 | 低负担验证 |
| --- | --- | --- |
| 场景选择比直接问城市偏好更容易回答 | 选项仍可能含糊，用户无法表达兼容或冲突需求 | 让少量目标用户独立走完，记录停顿、跳过和主动改句 |
| 画像让用户觉得选择被理解 | 只是把选项机械复述，没增加理解 | 看用户会修改哪一句、能否举出最近一周的对应情境 |
| 先见一城再反馈能发现关键取舍 | 用户只根据城市名反应，没有读理由 | 请用户指出具体心动点或代价，观察追问是否承接 |
| 猫狗不同侧重有帮助 | 角色名称掩盖了权重差异，让人误以为事实变了 | 切换后请用户解释哪里变了、哪些底线没变 |
| 现有证据能缩小探索范围 | 89 个未知使少数资料较多的城市占先 | 比较不同偏好下的理由，尤其检查关系与不确定性主导者是否得到虚假确信 |
| 一次短试住能验证生活假设 | 周末旅游体验不能代表普通工作周 | 按一个普通工作日和一个周末记录精力、相处、活动便利与实际代价 |

先找少量真实 AI 应用与产品目标用户发现明显问题，不用小样本满意度冒充准确率。下一步优先补对取舍有价值的生活场景证据和试住反馈；不默认扩成招聘或租房服务。

## Web、原生与 Agent 的实际边界

Web 已实现本地规则、五维画像与手动修订。OctoScript 原生版读取同一选项和权重配置，已有合成资料的原生与 JavaScript 对照记录；不能将此称为真实用户验证。

原生保留 CM1 的受控 Agent 提案机制：自由反馈、白名单提案、用户确认、保存和读回核验。但当前 CM1 不能修改五维场景；旧 `priority / focus` 可以保留在档案，却不影响 v0.3 Joy 排序。五维修订应通过场景按钮完成；气候和明确排除可按已有受控规则影响结果。不能把旧字段修改冒充“五维 Agent 已理解并执行”。

已有 card-host 生产路径与临时响应注入测试，不等于真实模型成功调用。本应用真实模型成功链路仍未验证。参赛定位和具体能力边界见 [场景说明](competition-fit.md)。
