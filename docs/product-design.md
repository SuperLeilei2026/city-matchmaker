# 毕业第一站：产品设计说明

版本：2026-10-03 晨间体验版。以下将已实现、设计判断与待验证假设分开记录。

## 一句话与使用场景

**毕业了，去哪座城认真生活？** 用户留下资料，认识一座城市，表达哪里不合适，再收下一份有依据、有代价的候选建议。

目标用户是毕业前后、行业大致有方向、但还没有确定生活城市的人。第一版的价值是缩小探索范围、说清自己在意什么。不能承诺预测未来会在哪儿更幸福。

## 体验为什么这样组织

| 环节 | 用户做什么 | 产品实际回应 |
| --- | --- | --- |
| 资料卡 | 按认识你、相处方式、工作生活三页填写，可跳过 | 本机保存、可直接切页、说明字段用途 |
| 第一个问题 | 行业未知则澄清行业，否则确认工作生活取舍 | 说明这次回答会改变什么 |
| 第一次介绍 | 看一座城市的具体理由与代价 | 每条理由连接明确需求、城市资料和证据状态 |
| 给反馈 | 选择心动、担心成本/天气/工作/太忙、明确拒绝、没感觉 | 反馈决定下一问；只有明确拒绝立即移出 |
| 再问一次 | 缩小真正影响决定的条件 | 条件可比较则重排，资料不足则增加核验事项 |
| 最后收敛 | 比较三个候选，翻看来源 | 回顾两轮确定的事，解释变与不变，同分不包装成唯一首选 |
| 分享 | 保存城市车票或复制摘要 | 输出城市与生活关键词，不泄露个人档案 |

两轮是控制体验长度的产品选择，尚无证据说明两轮足以准确推荐人生选择。预算、节奏等回答不一定改变排序：没有房源或地址时，应诚实留下核验项。

## 三个底层部分

**城市特点库**保存产业方向、生活资源、气候、资料来源与未知信息。城市“人格”是这些特点的可读表达，不是给居民贴 MBTI。

**个人画像**以明确回答为依据。行业、兴趣、优先级、气候底线和明确拒绝参与匹配。年龄区间、院校、MBTI、星座、欣赏的人格仅作背景；第一版未利用这些字段生成心理结论。用户要求保留这一类资料，因此允许填写，但不虚构其预测能力。

**匹配规则**先处理明确排除，再比较工作与生活，保留未知与同分。多兴趣共享生活权重；强调一种兴趣增加它在该组内的份额，不增加整个组的总权重。引擎为纯函数，修改资料后重算。

详细权重、证据规则与接口分别见 matching-model.md、CONTRACT.md。

## 角色、视觉与互动

INTJ 是已确认的黑白开脸德文猫，蓝色强调；ENFP 是已确认的线条小狗，橙色强调。两位介绍人共用同一匹配结论。猫直说理由和代价，狗增加标明为想象的生活片段。

整体采用暖白纸张、资料夹页签、印章、中文衬线大字和带撕线的城市车票。可操作的资料页签减少来回翻页；反馈直接承接下一问；结果回执展示已明确的选择；车票背面展示来源。尊重系统减少动画设置，手机页面适应窄屏。

“有人味”的落点是：问题有用途，回答被记住，不能判断的直说，用户的拒绝会产生效果。不靠增加闲聊或星座断言制造理解感。

## 分享设计与尚未证明的传播性

分享卡把复杂档案压缩成“我想先了解的城市＋我想留在生活里的事＋猫/狗介绍人”。它可以作为朋友聊天的起点。当前已实现本机生成 PNG 与复制摘要；没有公共访问链接，未做分享转化测试，不能称已经具有强传播效果。

优先验证三个观察：用户是否看懂产品在帮什么忙，结果中是否有一条具体理由值得讨论，是否愿意主动把卡发给朋友并解释原因。保存次数不等同于真正推荐满意。

## 关键假设与最短验证路径

| 假设 | 风险 | 验证方法 |
| --- | --- | --- |
| 先填资料比先聊天更愿意继续 | 三页资料可能负担过重，且部分背景暂不用于匹配 | 请5位真实目标用户从首页独立操作，观察停顿与退出点；尤其记录可选资料是否被误认为必填 |
| 看一座城再反馈能讲清偏好 | 用户可能只是对城市名有偏见，未读理由 | 首轮后请用户指出最不合适的一点，检查反馈是否具体、是否改变第二轮理解 |
| 两轮后更接近用户想要的生活 | 人工分档粗，数据缺失可能主导排序 | 对比首轮与次轮理由，让用户解释哪一轮更有帮助；不以点赞证明推荐准确 |
| 猫狗增强亲近感 | 角色可能掩盖内容薄弱 | 比较用户能否复述依据；切换风格后结论必须一致 |
| 自我介绍字段值得保留 | 字段填写后没有回报，会降低信任 | 测试背景折叠与完整资料两版；未加入经确认的有效追问前，不承诺人格理解 |

这5人是快速发现明显问题的小样本，不用于估计人群满意率。下一阶段最有价值的数据是岗位与住房生活圈的可比样本，以及用户为什么拒绝第一座城市。

## 参赛边界

Web 用于快速体验视觉与交互，OctoScript 包负责验证容器内的真实应用流程。原生版已具有系统 Agent 调用入口及失败回退，本机 card-host 没有对应服务；尚无本应用实际模型成功返回的证据。

正式参赛仍需：确认当前赛道对这一项目的适配；在完整 Shell 中完成真实系统 Agent；核对赛事当前规则；真实仓库、签名、Tag、App Hub Issue 与人工审核。已有 gate 通过不能代替上述步骤。
