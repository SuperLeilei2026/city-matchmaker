# 城市红娘匹配模型 v0.1

这是确定性的偏好比较器，不是人格测验、招聘预测或幸福概率模型。猫狗、MBTI、星座、年龄、院校和欣赏的人格不参与排序。城市“人格”和生活场景属于表达层。

## 三张逻辑表

1. 城市特点：`data/cities.json` 的 features、featureEvidence、sources、unknowns。数值为 0–3 的人工分档，必须保留来源或 editorial 标签；缺失不得补零冒充事实。
2. 个人偏好：Profile 的 industry、interests、focusInterest、priority、climateAvoids、hardClimate 等本人明确回答。confirmations 保存已答问题 id；feedback 保存 `{cityId, reasonId}`。focusInterest 是可选的生活重点，可为 null 或合法兴趣键；不会删除原兴趣。
3. 匹配规则：`core/matcher.mjs` 与 `core/questions.mjs`。前者每次从完整资料重算，后者选择下一问并生成无副作用的新资料。

## 分数与覆盖度

初版能够比较职业方向、生活资源、气候三个维度；成本、通勤、重要关系保留为核验项，不假装已经测量。不能把城市产业规模当个人录取机会，不能把全市设施当住处附近可达性。

工作／生活基础权重：career 为 0.65／0.35，balance 为 0.5／0.5，life 为 0.3／0.7。没选 priority 时暂按 balance，明确提示待确认。

若填写了气候避开项，工作与生活权重各乘 0.8，气候分配 0.2；否则气候权重为零。该调整对全部城市一致，不根据某座城市缺了什么资料重算分母。

- 职业：所选 industry 对应值除以 3。行业未知时，这一整个权重没有正向贡献。
- 生活：所有合法、去重后的 interests 均分生活权重；如果本人选了 focusInterest，该项分 2 份，其他每项 1 份，再按总份数分配生活权重。每项效用为对应值除以 3。增加多个兴趣或指定重点不会增加生活总权重；空选择保持该维度未知。
- 气候：去重后的避开项均分气候权重，每项效用为 `1 - value / 3`。
- score：各项权重乘效用之和乘 100，六位小数。它只是相对排序用的内部指标，页面不得称为幸福率、成功率或匹配准确率。
- coverage：有可用资料的权重之和，范围 0–1。未知的分数贡献和覆盖贡献都为零，绝不重新归一化使资料少的城市反而得高分。
- 同分按城市 id 的字典序稳定排序，这只是显示顺序，不代表有证据区分优劣。首位同分组标为 explore，同时在 missing 与各候选的 unknowns 中提示不能认定唯一首选。缺资料导致的低分不能解释为城市不适合；界面应同时展示待核验项。

有效资料必须是 0–3 的有限数值，并有 sourced 或 editorial 证据。sourced 还必须能在该城市 sources 中找到引用；悬空引用按未知处理。editorial 可用于带标签的探索排序，不能触发气候硬排除。

推荐理由直接取当前特征的 featureEvidence.note，不根据得分泛泛地说“资源丰富”。每条先确认本人需求，再给该城具体资料，最多两句；清理“人工分档”“记几分”等实现注释，保留实际岗位、场次、口味和日常可达性的限制。editorial 以“据现有资料整理”表达，并原样保留 reason.status 和 sourceIds。长 note 最多取 96 字符，优先在分句处截断；没有具体 note 时明确需要进一步核对，不补造事实。这层文案处理不修改效用或权重。

unknowns 说明还缺什么、会影响哪项决定，例如是否能常打球、住得安静、租金够用；不向使用者解释内部权重与分母。未清理的原始 note 仍保留在城市数据，便于核验。

coverage 至少 0.75、行业与兴趣已明确、气候硬条件没有缺证据，且不属于首位同分组时，状态为 candidate；其余为 explore。candidate 仍然不是就业、住房可行性的保证，结果中的 unknowns 始终保留。

## 硬条件与反馈

`not-this-city` 把城市从 ranked 移到 excluded。该拒绝同时存到 excludedCityIds 和 feedback，rankCities 兼容任一记录。其他反馈均不自行写硬条件；like 不能把被气候排除或已拒绝的城市带回来。

只有 `hardClimate: true` 且所避气候有 sourced 资料、人工分档达到 2 或 3，才排除城市。题面说明明确不合适会移出、资料不足则核验，不把分档公式塞进用户选项。资料为 unknown 或 editorial 时不贸然排除，也不宣称通过硬条件，而标 explore 和待核验。所有城市都不满足时返回空候选并解释，不能强推一城。

rentBudget 不能与 0–3 的成本分档直接换算。初版缺同口径、同住房类型的房租证据，所以不依据预算筛城或加分；所有预算仅成为明示的核验项。重要关系需要真实交通，禁止用经纬度距离代替时间。quiet／ball 需要街区级资料；城市库缺证据则为未知。

## 两轮问答

round=1：行业未知且未回答过时，先问职业方向；否则问职业／生活优先级；已回答则问实际休闲时段。问题都有 why，说明答案会改变什么。

round=2：跟随最后一条反馈。cost 问房租预算；climate 问具体不适或软硬程度；career 澄清职业方向；too-busy 区分嘈杂、工作占用和日常距离；like 核对休闲时段；拒绝／不确定用高频生活需求缩小方向。已确认的问题不重复，改问未解的信息缺口。

不是每个答案都应改变排名。预算、日常距离没有可比数据时，只能改变待核验清单；同一偏好被再次确认也可能保留原排序。应说明“为什么没变”，不制造排序变化。修改行业、优先级、实际兴趣或气候条件能依据真实规则改变结果。

applyAnswer 和 applyFeedback 深复制资料，不修改原对象。返回资料没有缓存结论，前端资料修订后必须重新调用 rankCities，并使旧结论失效。问题选项 patch 是内部可信配置，不应接收外部任意补丁。

## 验证

执行 `node --test tests/*.test.mjs`。测试覆盖硬气候、未知／悬空证据、不重复加权、拒绝、同分、人格隔离、预算与交通边界、资料修订、纯函数行为、两轮不同回答造成改推。data-integration 使用最终城市数组验证完整流程；城市数据缺失会明确 skip，不能据此宣称集成已通过。
